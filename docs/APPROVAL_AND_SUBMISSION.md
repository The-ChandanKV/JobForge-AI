# Approval and submission

## Review an application

Run discovery from **Automation** or let the hourly worker process enabled boards. It prepares eligible, qualifying jobs and saves the review payload. In **Approval Queue**, filter by readiness, missing information, unsupported portal, rejection, failure, or submission. Sort by match score, discovery date, company, or posting date. The dashboard leaves unknown dates and scores blank or labels them unavailable.

Select **Review application** to inspect the original posting, destination, eligibility, skills, exact PDF version, completed fields and answers. The cover letter is an optional draft for manual use. Edit the resume in **Resume Studio**, then prepare the selected version. Use **Edit Application Answers** for the mock question or manual handoff notes. Greenhouse contact fields come from verified Profile facts. Refresh preparation after changing those facts.

Click **Approve & Submit** once. The dashboard moves to **Applications**, where the queued task, attempt, or receipt appears. Use **Reject Application** to decline a review. With **Review & Open Application**, inspect the prepared data and open the official employer URL. Record a receipt only after you have genuine confirmation.

For bulk review, open each application preview before selecting it. **Review selected submissions** lists the exact jobs, destinations, and resume versions in a final confirmation dialog. Each selected application must be ready and supported. The entire batch is checked in one database transaction. **Reject selected** rejects the shown set.

## How approval works

The server binds a SHA-256 hash to the exact application ID, job snapshot, destination, resume version and PDF hash, form signature, fields, and answers. It stores the approval and task in one transaction. Concurrent repeat clicks for the same hash return the original task. A profile, destination, form, answer or resume change prevents use of a stale approval. The worker rechecks eligibility and the prepared payload before it reserves a unique dispatch checkpoint.

The worker retries bounded preflight reads before dispatch. Once reserved, the provider gets at most one POST. An explicit provider receipt is required for **Submitted**. Definitive rejections are **Failed**. A timeout, inconclusive response, or interrupted dispatch enters **Submission uncertain** and requires evidence. The local mock can reconcile from its saved receipt. For real jobs, verify with the employer before recording an external confirmation. The application and export retain timestamps and diagnostic categories. Older preparation status codes and the two-step synthetic path remain available for compatibility.

## Provider capabilities

| Provider | Documented employer submission method | Required fields and resume | Verification and constraints | JobForge |
|---|---|---|---|---|
| Greenhouse | Job Board application POST for the exact board and job. It uses an employer-issued Job Board API key via HTTP Basic authentication. | First name, last name and email plus fields marked required by that job's form. A PDF can be sent as a multipart attachment. | Discover questions first and validate required fields locally. The adapter accepts explicit acknowledgment and stores its reference or hash. Unsupported questions, consent, changed forms and ambiguous results require review. | Implemented for an authorized, verified board. Transport tested with mocked responses. |
| Lever | Postings API application POST requires a key generated by a Lever Super Admin for the employer account. | Name and email at minimum, with employer-specific configuration. Resume uploads use multipart form data. | Success includes an application ID. The API cannot expose custom posting questions. It has rate limits and the official hosted form handles custom configurations. | Manual handoff using the official apply URL. |
| Ashby | Employer API submits the posting UUID and current form fields. Basic authentication and the `candidatesWrite` permission apply. | Required paths come from the specific job's form. Files can be inlined as multipart data or uploaded using a presigned handle. | Validate the response body, including form errors and application-limit blocks. A submitted form instance can be checked through `application.info` with `candidatesRead`. | Manual handoff using the official apply URL. |

## Enable a verified Greenhouse board

Use employer-provided credentials and obtain documented authorization for the exact board. Verify the employer contract in an approved sandbox, including required fields and the acknowledgment response. Store the verification reference and credentials in local environment settings. Restart both services, choose **Authorized employer API** in **Automation**, and explicitly enable individually approved submission. Reprepare an application to capture the current form, then review and approve it. [Configuration and permission checks](SUBMISSION_PERMISSIONS.md)

## Notifications

The **Notifications** page records ready reviews and submission outcomes. Configure the batch interval and desktop or email channels in **Automation**. Windows uses the interactive taskbar notification API and opens the Approval Queue when clicked. Desktop visibility depends on the Windows session and notification settings. Email review notifications require both the dashboard opt-in and explicit SMTP configuration. External notices contain counts or generic outcome text. [Windows taskbar notifications](https://learn.microsoft.com/en-us/dotnet/api/system.windows.forms.notifyicon.showballoontip)
